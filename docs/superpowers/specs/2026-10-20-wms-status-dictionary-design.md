# Словарь статусов — дизайн

## Цель

Сегодня одно и то же понятие ("что значит статус X и куда он ведёт")
размазано по трём местам: сроки списания (`wms_writeoff_terms`), правила
маршрутизации (`wms_routing_rules`) и захардкоженные в `tasks.js`
зона-предикаты (`isPresortStatus`/`isMarketplaceStatus`/`isPcStatus`/
`isWmiMpPcStatus`/`isPmBufferStatus` и т.д.). Это уже стоило сессии
нескольких раундов багов (см. коммиты сегодняшнего дня по календарю/
журналу покрытия) именно потому, что "какие статусы обязательны для
участка" нигде не было единым источником правды.

Цель этой фичи: единый "словарь статусов" -- таблица
`(отчёт, статус) -> название, срок списания, срок разбора по умолчанию,
участок по умолчанию` -- который становится точкой входа для (1)
классификации строки файла при построении выгрузки, (2) расчёта срока
списания, (3) расчёта готовности к выгрузке (срок разбора), (4) журнала
покрытия (`wms_upload_coverage_log`), (5) единого экрана админки со
списком статусов.

## Явно вне рамок

- Движок условий `wms_routing_rules` (conditions/AND-OR/операторы/
  приоритет/группировка/теги/`upload_offset_days` на уровне правила) --
  НЕ переписывается и НЕ упрощается. Остаётся ровно как есть.
- Filter-правила (`output_key='filter'`) -- не затрагиваются этой фичей,
  работают как сегодня.
- Экран админки правил маршрутизации -- не переделывается, только
  получает новую точку входа (предфильтр по статусу) и режим "все
  правила" (уже есть).
- Переклассификация активных задач (`wms_reclassify_active_item`,
  `wms_apply_routing_rules`, Sweep) -- не меняется, продолжает читать
  `wms_routing_rules` напрямую.

## Архитектура

### Новая таблица `wms_status_dictionary`

```sql
create table public.wms_status_dictionary (
    id uuid primary key default gen_random_uuid(),
    source_format text not null,          -- "отчёт": general/packaging/no_order/after_sale_movement
    status_code text not null,             -- трёхбуквенный код, UPPER
    label text not null default '',        -- расшифровка
    writeoff_days integer,                 -- срок списания (null = не списывается)
    default_upload_offset_days integer not null default 0, -- срок разбора по умолчанию
    default_task_type text,                -- участок по умолчанию (null = только фоллбэк отсутствует, строка пропускается)
    is_required_for_coverage boolean not null default true, -- нишевые статусы (сегодняшние Оклейка/USD/TMM) ставятся false
    is_active boolean not null default true,
    sort_order integer not null default 999,
    created_at timestamptz not null default timezone('utc', now()),
    updated_at timestamptz not null default timezone('utc', now()),
    unique (source_format, status_code)
);
```

`default_upload_offset_days` действует, когда у статуса 0 или 1 активных
правил маршрутизации (см. ниже) -- при 2+ правилах у каждого свой
`upload_offset_days`, словарное значение в этом случае не используется
для расчёта готовности (но остаётся как описательное поле/дефолт на
случай, если правила временно отключат).

### Связь с `wms_routing_rules` -- без новой колонки

`wms_routing_rules` не меняется структурно. "Какие правила относятся к
статусу X формата Y" вычисляется на лету: обходим `conditions` активных
правил этого `source_format` (и `output_key='zone'`, и `='filter'` --
обе разновидности могут тестировать статус и обе показываются в модалке
статуса для контекста), ищем листовые условия с `attribute = 'status'`,
извлекаем значения (`eq`/`in`/`not-in` дают конечный список статусов;
`contains`/`not_contains`/числовые операторы на атрибуте `status` --
редкий краевой случай, для него правило считается "не привязанным к
конкретному статусу" и не попадает ни в одну группу словаря, только в
общий список "все правила"). Функция `rulesForStatus(sourceFormat,
statusCode)` живёт в `tasks.js`, рядом с остальной логикой правил
(переиспользует уже загруженный `state.routingRules.rows`, без нового
запроса к БД).

Для расчёта "0/1/2+ правил" (срок разбора, выше) считаются ТОЛЬКО
`output_key='zone'` правила этого статуса -- filter-правила не
маршрутизируют и не несут самостоятельного срока разбора, они только
отсекают часть строк до того, как до маршрутизации вообще дойдёт.

### `wms_writeoff_terms` -- выводится из эксплуатации

`activeWriteoffStatusTerms()`/`writeoffDateInfoForRow()` читают
`writeoff_days` из словаря вместо отдельной таблицы. Таблица
`wms_writeoff_terms` и её админ-экран удаляются отдельной (последней)
задачей плана, после того как словарь подтверждён рабочим на проде.

## Классификация ШК и срок разбора

В `buildGeneralPreview`/аналогичных build-функциях:

1. Активные правила проверяются первыми (как сегодня, через
   `wms_evaluate_rule_batch`) -- участок и срок разбора берутся из
   сработавшего правила без изменений.
2. Если ни одно правило не сработало -- вместо вызова хардкод-функций
   (`hardcodeZoneFor`) ищем строку словаря по
   `(source_format, status_code строки)`. Нашли -- участок и срок
   разбора из строки словаря. Не нашли -- строка пропускается
   (`unmatchedCount`, то же поведение, что и сегодня).
3. Хардкод-функции (`isPresortStatus` и т.д.) становятся мёртвым кодом
   после перехода -- удаляются отдельной (предпоследней) задачей плана,
   не сразу, чтобы было куда откатиться первое время эксплуатации.

## Журнал покрытия (пересборка `wms_upload_coverage_log`)

Таблица создана сегодня (миграции 202610200001-3) с ключом
`(business_date, target_task_type, source_format)`. Перестраивается на
статусный ключ:

```sql
create table public.wms_upload_coverage_log (
    business_date date not null,
    source_format text not null,
    status_code text not null,
    rule_key text not null,   -- id правила (uuid::text) ИЛИ '__default__'
    checked_at timestamptz not null default timezone('utc', now()),
    primary key (business_date, source_format, status_code, rule_key)
);
```

- **Запись** (`logUploadCoverage`, как и сегодня -- по показанному
  оператору окну, не по факту появления строк в файле): для каждого
  обязательного статуса формата (`is_required_for_coverage=true` в
  словаре) берём его текущие активные правила; если их 0 -- одна запись
  с `rule_key='__default__'`; если 1+ -- по записи на каждое правило.
  Диапазон дат -- окно, как сегодня (`uploadWindowForModule`).
- **Чтение** (`dayCoveredForModule`): "обязательные статусы формата" --
  из словаря, а не из хардкод-константы `FORMAT_REQUIRED_ZONE_TASK_TYPES`
  (она удаляется). День закрыт для статуса, когда для каждого его
  `(rule-or-default)` либо есть запись в журнале на эту дату, либо срок
  разбора этого правила/дефолта для этой даты ещё не наступил (та же
  "потолок по самому мелкому офсету" логика, что уже отлажена сегодня
  для зон -- переносится один в один, просто единица учёта меняется с
  зоны на `(статус, правило-или-дефолт)`).
- **Бэкофилл** при развёртывании: источник истины -- `wms_task_items`
  (поле `status` на строке item, через `latinStatusCode`), а не окно
  рана (та ошибка уже стоила сегодня отдельного фикса -- общее окно
  рана "блендит" разные статусы/зоны одного файла). Join
  `wms_task_items -> wms_tasks` (для `upload_effective_date`,
  `task_type`), `latinStatusCode(item.status)` даёt статус, текущие
  активные правила этого статуса+task_type определяют `rule_key` (или
  `__default__`, если совпадающих правил не нашлось). Проверяется
  вживую тем же способом, что и сегодняшний бэкофилл (prod-запрос перед
  миграцией, begin/rollback тест, сверка агрегатов по датам до/после).

## Админка

Новый экран "Статусы": таблица словаря (отчёт, статус, название, срок
списания, срок разбора, участок, обязателен, активен). Клик по строке
открывает существующую модалку правил маршрутизации, предфильтрованную
по этому статусу (`rulesForStatus`), с переключателем "этот статус / все
правила" (второй режим -- сегодняшний полный список без изменений).
Создание/редактирование строки словаря -- отдельная форма на этом же
экране (по аналогии с существующей формой правил).

## Миграция данных (сид словаря)

Один раз при разворачивании: статусы собираются из (а) всех значений
`status`, встречающихся в `conditions` активных правил по каждому
`source_format`, (б) всех строк `wms_writeoff_terms` с
`term_type='status'`. `default_task_type` сидируется из самого частого
`target_task_type` среди правил этого статуса (если правило одно --
однозначно; если правил нет для статуса, который сегодня распознаётся
хардкод-функцией, `default_task_type` берётся из соответствия той
хардкод-функции). `writeoff_days`/`label` -- из `wms_writeoff_terms`,
где есть совпадение по ключу. Сид не обязан быть идеальным с первого
раза -- новый экран сразу даёt это поправить руками до переключения
классификации (этап 2 ниже).

## Поэтапная раскатка

1. **Таблица словаря + сид + экран админки.** Чисто аддитивно, ничего
   в построении выгрузок/журнале покрытия не меняется. Можно проверить
   и поправить данные глазами до следующего этапа.
2. **Классификация и срок списания/разбора переключаются на словарь**
   (фоллбэк вместо хардкода, `writeoff_days` вместо `wms_writeoff_terms`).
3. **Журнал покрытия пересобирается на статусный ключ** (новая таблица,
   бэкофилл из `wms_task_items`, `dayCoveredForModule`/
   `logUploadCoverage` переписаны).
4. **Чистка мёртвого кода**: хардкод-предикаты, `wms_writeoff_terms` и
   её админ-экран, `FORMAT_REQUIRED_ZONE_TASK_TYPES`.

Каждый этап -- отдельная проверяемая задача (SQL: begin/rollback с
синтетикой + regression на реальных данных; JS: `node --check tasks.js`),
коммит и пуш после подтверждения, как и весь сегодняшний день.

## Риски

- Сид словаря из живых правил может пропустить статус, который сегодня
  обрабатывается ТОЛЬКО хардкод-функцией без единого активного правила
  (напр. если для какой-то ветки правило никогда не заводили) -- на
  этапе 1 это видно по пустым/неполным строкам словаря до переключения,
  не ломает прод.
- `rulesForStatus` на условиях с нестандартными операторами (contains/
  числовые на атрибуте `status`) не определяет принадлежность статусу --
  редкий случай по сегодняшнему живому аудиту правил (все general-правила
  используют `eq` на статусе), но стоит перепроверить живым запросом
  перед этапом 2.
