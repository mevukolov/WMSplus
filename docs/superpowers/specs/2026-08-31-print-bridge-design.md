# Мост печати на термопринтер — дизайн

## Цель

Дать любому сотруднику печатать термоэтикетки (50×50 мм: ШК-штрихкод, QR, текст,
в разных сочетаниях по типу этикетки) с кнопки на сайте WMS+, на один общий
сетевой термопринтер (TSC DA220) — без установки драйверов на каждом ПК и без
локального сервера на каждом рабочем месте.

## Ключевое ограничение, определяющее архитектуру

Браузер не может открыть сырой TCP-сокет до устройства в локальной сети —
в вебе нет соответствующего API. Термопринтеры вроде DA220 обычно принимают
команды печати (TSPL) именно так — сырыми байтами по TCP, обычно на порт 9100
(стандарт AppSocket/JetDirect). Значит между кнопкой на сайте и принтером
всегда нужен хотя бы один посредник с доступом к локальной сети склада.

Решение: **один** лёгкий процесс-мост на складе (не на каждом ПК), плюс
очередь заданий в Supabase, через которую сайт и мост общаются, не завися от
того, находится ли конкретный ПК пользователя в одной сети с принтером.

## Компоненты

### 1. `print_label_templates` (таблица Supabase)

Описание макета этикетки как данных, а не кода.

| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | |
| `name` | text | Человекочитаемое имя шаблона |
| `width_mm` / `height_mm` | numeric | Размер этикетки (сейчас всегда 50×50, но не хардкодим) |
| `elements` | jsonb | Массив элементов макета (см. ниже) |
| `created_at` / `updated_at` | timestamptz | |

Элемент `elements[i]`:

```json
{
  "type": "barcode" | "qr" | "text",
  "field": "shk",            // имя переменной из данных задания, ЛИБО
  "literal": "ПРИВЕТ",       // статический текст (взаимоисключимо с field)
  "x_mm": 5,
  "y_mm": 5,
  "width_mm": 40,            // для barcode/qr
  "height_mm": 15,           // для barcode/text
  "font_size": 10,           // для text
  "barcode_type": "code128"  // для barcode: code128 | ean13 | ...
}
```

Формат сознательно простой (плоский список абсолютно позиционированных
элементов) — без вложенности, без условной логики. Этого достаточно для
термоэтикетки с ШК/QR/текстом и не создаёт лишней сложности, которую пришлось
бы поддерживать.

### 2. Админка шаблонов (новая страница на сайте)

Форма, не визуальный редактор: список элементов, у каждого — тип (select),
поле или статический текст, X/Y/размер (числовые инпуты), предпросмотр не
обязателен для v1 (можно проверить сразу через тестовую страницу печати).
CRUD над `print_label_templates`.

Явное решение по объёму: drag-and-drop/WYSIWYG редактор — не в этой версии.
Если понадобится позже, он строится поверх той же структуры данных
(`elements`), без миграции существующих шаблонов.

### 3. `print_jobs` (таблица Supabase)

| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | |
| `template_id` | uuid (FK) | |
| `data` | jsonb | Значения полей для этого конкретного задания (`{"shk": "123456"}`) |
| `tspl` | text | Уже готовый текст TSPL-команды — собирает сайт при создании задания |
| `status` | text | `queued` \| `printed` \| `failed` |
| `error_message` | text \| null | Заполняется мостом при `failed` |
| `created_at` / `created_by` / `printed_at` | | |

Сайт вставляет строку со статусом `queued` и сразу подписывается на неё
(Supabase Realtime) — так интерфейс узнаёт об успехе/ошибке.

### 4. Модуль сборки TSPL (JS, общий код на сайте)

Функция `buildTsplFromTemplate(template, data) → string`, читает
`template.elements`, для каждого элемента подставляет значение из `data`
(или `literal`), переводит мм в точки принтера (dpi берётся из конфигурации
принтера — уточним при первом реальном тесте, см. риск ниже), и собирает
итоговый TSPL-текст. Один модуль — переиспользуется тестовой страницей сейчас,
и позже любым местом сайта, откуда понадобится печать (разбор, предсписок).

### 5. Тестовая страница печати (новая, отдельная от разбора/предсписка)

- Выбор шаблона (dropdown, значения из `print_label_templates`).
- Форма для значений полей — строится динамически по `elements` выбранного
  шаблона (одно текстовое поле на каждый `field`).
- Кнопка «Печать»: `buildTsplFromTemplate()` → запись в `print_jobs` со
  статусом `queued` → подписка на статус этой записи → индикатор
  (спиннер → «Напечатано ✓» / «Ошибка: …»).

Первая версия сознательно не встроена в карточки разбора/предсписка — это
следующий шаг, когда основной механизм подтверждён на реальном принтере.

### 6. Мост (Node.js-процесс на складе, один экземпляр)

- Подписывается на `print_jobs` с `status = 'queued'` (Supabase Realtime
  или короткий polling — решим в плане реализации).
- На каждое задание: открывает TCP-сокет на `IP_принтера:9100`, отправляет
  `tspl` как есть, по подтверждению — `status = 'printed'`, по ошибке —
  `status = 'failed'` + `error_message`.
- Никакой логики этикеток внутри — чистый ретранслятор. Не содержит
  секретов, видимых пользователям сайта (IP принтера, ключ доступа к
  Supabase — только в конфигурации этого процесса).
- Не требует передеплоя при добавлении нового типа этикетки — тот живёт
  только в данных (`print_label_templates`).

## Данные пользователя, которые нужны мосту

- IP-адрес принтера в локальной сети склада (конфигурация моста).
- Учётные данные Supabase с правом читать/писать `print_jobs` (service-key
  или аналог, только в конфигурации моста, не в браузере).

## Риск, не проверенный на практике

Реальный протокол TSC DA220 (сырой TSPL на порт 9100, разрешение в
точках/мм для перевода координат) — предположение, основанное на типовом
поведении термопринтеров этого класса, но не подтверждённое на этой
конкретной модели. Это нельзя проверить без доступа к реальной сети склада.
План: первым шагом при развёртывании моста на месте — отправить один
простой тестовый TSPL-текст напрямую (например через `nc IP 9100 < test.tspl`
или штатную утилиту TSC Diagnostic Tool) и подтвердить, что этикетка
печатается предсказуемо, прежде чем полагаться на архитектуру в проде.

## Явно не входит в первую версию

- Визуальный (drag-and-drop) редактор шаблонов.
- Встраивание кнопки печати в существующие карточки разбора/предсписка.
- Очередь с приоритетами/переупорядочиванием — задания печатаются в порядке
  поступления.
- Повторная печать неудачного задания одним кликом (можно создать job
  заново вручную).
- Ограничение доступа к печати по ролям — предполагается, что печатать
  может любой залогиненный пользователь WMS+.
