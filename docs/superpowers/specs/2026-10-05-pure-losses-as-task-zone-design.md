# «Чистые списания» как зона разбора внутри wms_tasks — дизайн

**Спек:** продолжает и частично заменяет раздел «Как ШК на самом деле
становится «Списан»» в
[docs/superpowers/specs/2026-10-02-wms-entity-glossary-design.md](./2026-10-02-wms-entity-glossary-design.md).
Та версия («закрыть задачу на месте вердиктом «Система - Автосписание»»)
оказалась неверной — решала только половину задачи и не поддерживала
обратный переход. Этот документ — исправленный, полный дизайн.

## Цель

«Чистые списания» (`pure_losses_rep`, экран `pure_losses.html`) сегодня —
отдельный, не связанный с задачами архив со своим decision-UI
(`applyVerdictSelection`), без механизма отложения. Задача (`wms_tasks`) и
чистые списания живут параллельно: тот же физический товар (ШК) может
одновременно существовать как незавершённая задача И как строка списания,
без какой-либо связи между ними.

Нужно: при появлении ШК в выгрузке чистых списаний — его единственное
актуальное представление должно стать задачей в новой зоне разбора
«Чистые списания» внутри `wms_tasks`, с собственным (слегка урезанным)
набором вердиктов и возможностью отложения, как у любой другой задачи.
Если впоследствии тот же ШК снова всплывёт в любой другой выгрузке — он
должен вернуться обратно в ту зону, перенеся всю историю.

## Почему именно так — прецедент уже есть

Разные «участки» (Предсортировка, АВХ, Коробки на входе) — это не разные
таблицы, это разные значения `task_type`/`source_module` внутри одной и
той же `wms_tasks`. «Чистые списания» как ещё одна зона разбора — это
ровно то же самое, просто ещё одно значение `task_type`.

Благодаря этому перенос «со всей историей» получается почти бесплатно:
`wms_task_history` привязана к `task_id`, который не меняется при смене
зоны — переключаем у задачи `task_type`/`task_status`/`opp_verdict` на
месте, и вся прошлая история (из любой предыдущей зоны, включая фазу
«Чистые списания») остаётся на той же строке автоматически. Альтернатива
(копировать/мёрджить данные между отдельными таблицами при каждом
переходе) была рассмотрена и отклонена — требует явного переноса истории
в обе стороны и рискует разойтись.

## Прямой переход: любая задача → «Чистые списания»

Триггер: загрузка Excel-файла чистых списаний в `pure_losses.js`
(`processImport`, тот же вызов, что сегодня идёт в
`wms_reconcile_shks_written_off` — эта RPC переписывается, см. ниже).

Для каждого ШК из выгрузки, которого в данных помечено как списанный:

1. **Ищем существующую незавершённую задачу** с этим ШК, у которой
   `task_type <> 'Чистые списания'` (та же логика поиска, что уже есть —
   `source_shk_ids && p_shks`).
2. **Одиночная задача** (этот ШК — единственный в задаче) → **переиспользуем
   ту же строку**: `task_type = 'Чистые списания'`, `task_status = 'Не
   начато'`, `opp_verdict = 'Не выбран'`, `source_payload`/цена/наименование
   обновляются из данных чистых списаний (теперь это авторитетный источник).
   В `wms_task_history` пишется запись о переходе — с **реальным временем
   списания** (`date_lost` из чистых списаний), не временем обработки
   файла.
3. **ШК внутри тары** с другими активными товарами → вынимаем его из тары
   на месте (как уже сделано в текущей `wms_reconcile_shks_written_off` —
   этот кусок логики переносится без изменений), и ДЛЯ ЭТОГО ОДНОГО ШК
   создаём **новую** строку с `task_type = 'Чистые списания'` (тару
   целиком переиспользовать нельзя — остальные товары остаются в работе).
   Новая строка несёт `source_payload.split_from_task_id`, как и обычное
   разделение тары (`splitTaskFromTare`).
4. **Задачи с этим ШК нет вообще** → создаём новую строку с `task_type =
   'Чистые списания'` напрямую из данных чистых списаний.

## Обратный переход: любая выгрузка → ШК выходит из «Чистые списания»

Триггер: **не отдельный хук** — встраивается в уже существующий общий
механизм дедупликации по ШК внутри `save_wms_manual_upload` (единственная
точка создания задач, используется абсолютно всеми модулями/выгрузками).

Сегодня эта функция, найдя существующую незакрытую задачу с тем же ШК из
ДРУГОГО модуля, просто дописывает ей историческую пометку
(`task_cross_module_touch`) и не трогает статус. Меняется:

- Если у найденной канонической задачи `task_type = 'Чистые списания'` —
  вместо пометки **переключаем её обратно**: `task_type`/`task_status`/
  `opp_verdict` сбрасываются на значения новой выгрузки (обычно «Не
  начато»/«Не выбран»), `source_payload`/цена/наименование обновляются из
  новой выгрузки. История — та же строка, тащится автоматически.
- Если `task_type` у найденной задачи — что угодно ДРУГОЕ (не «Чистые
  списания») — поведение не меняется, работает как сегодня
  (`task_cross_module_touch`, статус не трогается).

Это симметрично прямому переходу и использует ровно тот же принцип
(переключение `task_type` на месте).

## Вердикты зоны «Чистые списания»

Отдельный список, не трогает список обычных участков (`REVIEW_VERDICTS`
для всех прочих зон остаётся как есть, включая «Отправлен на релиз» и
«Аннулирование после списания» — они никуда не делись для ОБЫЧНЫХ задач):

- Найден/Релиз/Списан
- Отправлен запрос
- Нет на МХ/Не найден
- Отправлен на списание ревизией
- Исключён из автосписания
- **Отправлен на аннулирование** (новый) — отложение на 2 дня, та же
  механика `reopenAfterForVerdict`, что у остальных отложенных вердиктов
  (`task_status = 'Отложено'`, `reopen_after = now() + 2 days`, резюрфейсится
  автоматически тем же механизмом, что даёт `task_auto_reopened`).

Технически: `REVIEW_VERDICTS` остаётся как есть; добавляется отдельная
структура (например `ZONE_VERDICTS` с ключом по `task_type`), которая для
зоны «Чистые списания» переопределяет список, остальные зоны продолжают
читать общий `REVIEW_VERDICTS`.

## `pure_losses.html` / `pure_losses.js`

Перестаёт быть экраном разбора. `applyVerdictSelection` и весь
decision-UI (модалка выбора вердикта, цветные пилюли по `decision`)
убираются из рабочего использования — разбор теперь идёт в `tasks.js`
через зону «Чистые списания». `pure_losses_rep` остаётся сырым
леджером-источником: отсюда берётся сам факт «этот ШК считается
списанным» и дата списания, возможно сохраняется отчётность/статистика
поверх него, но не рабочая очередь принятия решений.

(Конкретный объём того, что в `pure_losses.js` убирается физически, а что
остаётся как read-only отчёт — предмет самого плана реализации, не этого
дизайн-документа.)

## Что происходит с уже задеплоенным

`wms_reconcile_shks_written_off` (миграции `202610020004`/`202610020005`,
вердикт «Система - Автосписание») переписывается под логику «прямого
перехода» выше — вместо «закрыть на месте» теперь «переключить/создать
строку в зоне «Чистые списания»». Отдельный вердикт «Система -
Автосписание» как таковой, по всей видимости, не нужен вовсе: сама зона
«Чистые списания» + обычный вердикт, выставленный уже там человеком —
это и есть ответ на вопрос «списан». `SYSTEM_AUTO_WRITEOFF_VERDICT`
(task-verdicts.js) и его регистрация в `SYSTEM_COMPLETION_VERDICT_KEYS`/
`SYSTEM_VERDICT_SET` (tasks.js) убираются как часть реализации плана.

## Открытые вопросы (не блокируют план, но план должен их явно решить)

- Точный механизм группировки "зона/участок" в review-UI (`taskSectionName`
  и подобное) — убедиться, что зона «Чистые списания» естественно ложится
  в существующую систему группировки участков, не требуя отдельного
  спецкейса.
- Объём физической чистки `pure_losses.js` (что убрать, что оставить как
  read-only) — решается в плане, не здесь.
- Нужна ли зоне «Чистые списания» своя денормализованная метка на карточке
  задачи (например «Из чистых списаний: списан 12.09, вернулся 20.09») —
  не запрошено явно пользователем, не включено в текущий дизайн.
