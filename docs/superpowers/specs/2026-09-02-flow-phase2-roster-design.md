# Флоу, Фаза 2 (часть 1) — Ростер смены

Дата: 2026-09-02
Статус: одобрено пользователем, готово к планированию реализации

## Контекст

Фаза 1 (движок/UX Флоу) уже в `main`: непрерывная лента, единая
встроенная карточка, полноценный предсписок внутри ленты, дебаг-песочница.
Модель зон при этом осталась той же, что была в MVP — ровно два именных
человека на смену (`wms_shifts.incoming_employee_id`/`outgoing_employee_id`),
привязанных к двум зонам ("Входящий поток"/"Исходящий поток").

На практике это распределение уже не отражает реальную работу: почти все
модули загрузки (`DEFAULT_MODULES` — Упаковка, RWP, ПМ, Предсортировка,
Маркетплейс, ПЦ, WMI, Без заказа, USD, TMM, Движение после продажи)
попадают в одну и ту же зону "Исходящий поток" (см. `taskSectionForAchievement`/
`responsibilityZone` по всему `tasks.js`), а "Входящий поток" — это по сути
только Запросы. То есть весь большой общий разбор сейчас в скоринге
Флоу считается "своей зоной" только для одного зафиксированного человека,
хотя реально его параллельно разбирает вся смена.

Фаза 2 разбита пользователем на 4 независимых куска: **Ростер → Диспетчер
→ QA-экран → Личный коэффициент**, каждый со своим циклом
дизайн/план/реализация. Этот документ — только первый кусок, Ростер.

## Цель

Заменить два жёстко зашитых именных поля на список сотрудников смены,
каждый из которых может отвечать за несколько участков одновременно, и
завести зоны скоринга Флоу на этот список вместо текущей бинарной проверки
"входящий/исходящий".

## Явно не входит в этот документ

- Серверный диспетчер, атомарный захват задачи — Фаза 2, часть 2, отдельный
  дизайн.
- Экран ручной QA-проверки — часть 3.
- Личный коэффициент (4 сигнала) — часть 4, зависит от части 3.
- Формула скоринга внутри `flowScoreTask` (веса, история, теги, ценовые
  бусты) — не меняется, кроме самого способа определить "своя ли это зона".
- Миграция/удаление старых колонок `incoming_employee_id`/`outgoing_employee_id`
  из `wms_shifts` — остаются в схеме нетронутыми (могла быть завязана
  историческая отчётность вне этого файла), просто перестают заполняться
  для новых смен.

## Дизайн

### Модель данных

Новая колонка `wms_shifts.roster jsonb not null default '[]'::jsonb`.
Формат — массив объектов:

```json
[
  { "employee_id": "1034305", "full_name": "Иванов Иван", "zones": ["ПЦ", "Маркетплейс"] },
  { "employee_id": "2048177", "full_name": "Петров Пётр", "zones": ["Упаковка"] }
]
```

Зоны — ровно 14 существующих значений `REVIEW_SECTIONS` (Упаковка, RWP,
ПМ, Почта, Предсортировка, Маркетплейс, ПЦ, WMI (МП + ПЦ), Без заказа,
Движение после продажи, Другие задачи) + `REQUEST_SECTIONS` (Запросы
входящего потока, Списания AWH, Коробки на входе) — та же номенклатура,
которой уже фильтруется классический разбор, без новой терминологии.
Один человек может входить в ростер с несколькими зонами; один и тот же
человек не должен фигурировать дважды в массиве (при редактировании —
объединять зоны, а не добавлять вторую запись).

`incoming_employee_id`/`outgoing_employee_id`/`incoming_process`/
`outgoing_process` в `saveShiftOpening` больше не заполняются для новых
смен, но остаются читаемыми для уже открытых смен, где `roster` пуст
(см. "Обратная совместимость" ниже).

### UI: модалка «Открыть смену»

Два `<select>` ("Входящий"/"Исходящий") заменяются на список
"сотрудник → чекбоксы участков" с кнопкой «+ добавить человека»:
каждая строка — выбор сотрудника (тот же источник, что и сейчас питает
`fillShiftSelects`/`employeeById`) плюс 14 чекбоксов зон. Удаление строки —
крестик у строки. Валидация сохранения (`updateShiftOpeningForm`): нужен
хотя бы один человек с хотя бы одной зоной (вместо текущего "оба select
заполнены").

Повторное открытие модалки для уже открытой сегодня смены подгружает
текущий `roster` и позволяет его отредактировать (добавить/убрать людей
или зоны) и пересохранить — отдельного экрана редактирования ростера в
течение дня не создаётся, как и раньше с двумя ролями.

### Скоринг зон

`currentFlowEmployee()` перестаёт сравнивать `id` с двумя конкретными
полями и вместо `zones: Set<"incoming"|"outgoing">` возвращает
`zones: Set<строка-участок>` — все зоны текущего пользователя из
`state.shift.current.roster`, найденные по `employee_id` или по имени
(тот же двойной fallback id/имя, что и сейчас, ради устойчивости к уже
знакомой проблеме с "разъехавшимися" `wms_employees.full_name`).

`flowTaskSection(row)` (уже существует: `requestSectionName(row) ||
taskSectionName(row)`, корректно различает запросы и обычный разбор) —
это и есть канонический "участок задачи", проверяем его на вхождение в
`zones` текущего пользователя. Новая `flowRowIsOwnZone(row, context)`
заменяет `flowTaskZoneKey`'s бинарную "incoming/outgoing/neutral" логику
этой проверкой. `flowTaskZoneLabel(row)` (сейчас превращает ключ обратно
в "Входящий поток"/"Исходящий поток"/"Нет привязки" для отображения в
карточке) упрощается до прямого возврата `flowTaskSection(row)` —
показываем реальное название участка ("ПЦ", "Упаковка"), а не
искусственную бинарную метку. `zone.own`/`otherFlexible`/`strictBonus`
из `wms_flow_score_settings` применяются как и раньше, просто к
результату новой функции — сама формула и веса не меняются.
`FLOW_STRICT_INCOMING_SECTIONS`/`FLOW_STRICT_OUTGOING_SECTIONS`
схлопываются в один `FLOW_STRICT_SECTIONS = new Set(["Запросы входящего
потока", "Коробки на входе", "Списания AWH"])` — раньше их искусственно
делили на "входящие"/"исходящие" только чтобы завязать на два зонных
ключа, что было нужно только текущей бинарной модели; `flowZonePolicy`
проверяет вхождение в это одно множество, поведение не меняется.

### Дефолтный assignee на новых задачах

`shiftAssigneeForZone(zone)` вместо `id.includes("вход") ? incoming :
outgoing` ищет первую запись в `roster`, у которой зона участка задачи
есть в списке зон, и возвращает её сотрудника. Если для зоны в ростере
никого нет — как и сейчас, `assignee_employee_id`/`assignee_name`
остаются пустыми (задача просто без дефолтного исполнителя, ничего не
ломается — это чисто предзаполнение для классической таблицы «Разбор»,
реальное распределение всегда происходит через явное действие
сотрудника: клейм в Флоу или открытие/завершение в классике).

### Обратная совместимость

Смены, открытые до этого изменения (есть `incoming_employee_id`/
`outgoing_employee_id`, `roster` пуст/отсутствует), на лету
конвертируются в ростер при чтении: `incoming_employee_id` →
`{zones: ["Запросы входящего потока", "Коробки на входе"]}`,
`outgoing_employee_id` → `{zones: [все остальные 11 участков]}` — то
есть старые данные читаются так, будто это была смена с ростером из
двух широких зон, эквивалентно текущему поведению. Эта конвертация —
чистая функция чтения (`normalizeShiftRoster(shift)`), нигде не
перезаписывает старые поля в базе.

## Риски и открытые моменты для этапа реализации

- Нужно решить порядок отображения/добавления людей в UI ростера
  (алфавитный список сотрудников склада — откуда он берётся сейчас для
  `fillShiftSelects`, тот же источник подойдёт для нового мультиселекта).
- Нужно проверить вживую после реализации: смена, открытая ДО изменения
  (с двумя старыми полями), должна давать идентичный скоринг зон после
  конвертации — сравнить `flowScoreTask` до/после на одной и той же
  реальной смене.
- `taskSectionForAchievement(row)` (используется в подсчёте ачивок/личной
  статистики) — отдельная функция от `flowTaskSection`, стоит при
  реализации сверить, что она возвращает то же самое значение для всех
  14 участков (иначе личная статистика и зонный бонус будут расходиться
  в понимании "какой это участок" для одной и той же задачи).

## Проверка

Ручная проверка в браузере: открыть смену с 3+ людьми на разные и
частично пересекающиеся участки, убедиться что каждый в Флоу видит
бонус "своя зона" ровно на тех участках, что отметил себе в ростере;
конвертация старой (двух-ролевой) смены даёт тот же скоринг, что и до
изменения; классическая таблица «Разбор» по-прежнему получает дефолтного
исполнителя на новых задачах.
