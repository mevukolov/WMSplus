# Унификация загрузок через движок правил — дизайн

**Спека.** Этот документ фиксирует согласованный дизайн для writing-plans. Контекст и ход обсуждения — в сессии; здесь только финальные решения.

## Цель

Сегодня 8 кнопок загрузки ("Выгрузить предсортировку", "Выгрузить упаковку" и т.д.), каждая со своей JS-функцией `build*Preview` и частично захардкоженной классификацией/группировкой/приоритетом/сроками. Цель — убрать привязку "кнопка = участок" и заменить на "кнопка = формат файла", передав ВСЮ классификацию (куда положить, группировать ли, с каким приоритетом, с каким сроком, отсеивать ли вообще) в движок правил `wms_routing_rules`, admin-конфигурируемый без правок кода.

## Текущее состояние (установлено исследованием)

Реальных форматов колонок — 3, не 8:

- **`general`** (сегодняшний `kind: "pmPrimary"`, функция `normalizePmPrimaryRow`) — общий для ПМ (основной файл), Предсортировка, Маркетплейс+ПЦ, WMI, Без заказа. У Предсортировки/Маркетплейс+ПЦ/WMI/ПМ инструкция в UI буквально одна и та же ("Товары без движения - В заказе"); "Без заказа" — тот же отчёт, просто с фильтром "В заказе/Без заказа" при выгрузке из ресурса (подтверждено пользователем).
- **`packaging`** (`normalizePackagingRow`) — общий для Упаковки и RWP, один и тот же внешний отчёт ("Утерянные и обездвиженные товары" → "Обездвижено"); разделение Упаковка/RWP уже сегодня делается по статусу строки (`isRwpStatus`), не по кнопке.
- **`after_sale_movement`** (`normalizeAfterSaleMovementRow`, 2 авто-определяемых варианта колонок v1/v2) — свой формат, единственный участник. Пользователь явно попросил тоже перевести его на движок, несмотря на отсутствие дублирования, ради единообразия админки.

ПМ держит отдельный второй файл ("проверка отгрузки") — сегодня блокирует сохранение, если передача уже отгружена. Выносится из этой унификации в отдельное действие (см. раздел 6).

## Архитектура

### 1. Расширение `wms_routing_rules`

Новые колонки:

`output_key` уже исторически играет роль "вид правила" (раньше `'zone'`/`'no_order_folder'`, сейчас всегда `'zone'`) — вместо новой отдельной колонки переиспользуем его: добавляем допустимое значение `'filter'`. Отдельная `rule_kind`-колонка не создаётся (не дублируем дискриминатор).

| Колонка | Тип | Назначение |
|---|---|---|
| `output_key` (существующая) | добавить допустимое значение `'filter'` в check-constraint | `'zone'` — маршрутизация (как сейчас); `'filter'` — отсечь строку, задачу не создавать. |
| `source_format` | `text not null`, check `in ('general','packaging','after_sale_movement')` | В какой загрузке правило вообще участвует. |
| `force_tare_grouping` | `boolean not null default false` | Чекбокс "Группировать по таре" (замена `forceTareGrouping`). |
| `force_high_priority` | `boolean not null default false` | Чекбокс "Высокий приоритет" (замена `forceHighPriority`). |
| `tags` | `text[] not null default '{}'` | Замена захардкоженных `tags: [...]` (напр. "Идентификация из ОПП", "почта"). |
| `task_deadline_days` | `integer` | Срок выполнения, дней (замена `taskDeadlineDays`/`pmDeadlineDays`/`mailDeadlineDays`). `null` → используется дефолт участка на переходный период. |
| `upload_offset_days` | `integer not null default 0` | "Окно выгрузки" — замена `offsetDays` (-7 Упаковка, -4 RWP, 0 остальные). |

`'filter'`-правила не используют `target_task_type`/`from_zone`/группировку/приоритет/теги/срок — только `conditions` + `source_format`. Существующий уникальный индекс на `(output_key, priority)` не меняется — `output_key='filter'` уже даёт filter-правилам свою, независимую от zone-правил нумерацию приоритета бесплатно.

### 2. Новый атрибут условия: `price`

`wms_rule_conditions_match` уже attribute-agnostic (`p_attributes->>v_attr`) — **правок самой SQL-функции не требуется**. Нужно только передавать `price` в jsonb атрибутов на этапе построения выгрузки (`zoneRuleAttributesForRow`/эквивалент для фильтров). Числовые операторы (`gt`/`gte`/`lt`/`lte`/`between`) уже есть.

`wms_evaluate_rule_batch(p_output_key text, p_rows jsonb)` сегодня матчит ПРОСТО по `output_key`, без учёта формата — для единственного сегодняшнего формата этого хватало. С появлением `source_format` функция должна получить новый обязательный параметр `p_source_format text` и фильтровать `where is_active and output_key = p_output_key and source_format = p_source_format` — иначе filter/zone-правило одного формата может случайно сработать на строке другого формата с похожими условиями.

Проверка "МХ содержит коробки" не получает отдельного атрибута — выражается существующим условием `mx` + `not_contains` + `"коробк"`, как указал пользователь.

`price` — только build-time атрибут (для Filter-правил при построении выгрузки). В переклассификацию (`wms_compute_reroute_target`) не добавляется: цена не трекается по уже сохранённым `wms_task_items`, и переклассификация не создаёт/не отменяет задачи — только меняет зону.

### 3. Единый пайплайн построения выгрузки (вместо 7 функций)

Новая общая `buildUnifiedPreview(sourceFormat, rows, businessDate)`:

1. Распарсить файл по формату (`general`/`packaging`/`after_sale_movement`) — парсинг колонок остаётся как есть, просто подключается к одной из 3 кнопок вместо 8.
2. Прогнать активные **filter**-правила этого `source_format` (по приоритету, первое совпадение отсекает строку — как сегодня работает zone-движок). Отсеянные строки идут в разбивку "отфильтровано: <имя правила>" для UI предпросмотра.
3. Прогнать активные **zone**-правила на оставшихся строках (без предварительной фильтрации по дате — важное изменение порядка, см. ниже).
4. Для строки, совпавшей с zone-правилом: проверить **окно выгрузки** — дата строки (поле зависит от формата: `created_at` для `general`, `last_movement` для `packaging`, `status_at` для `after_sale_movement`) должна равняться `businessDate − upload_offset_days` этого правила. Не совпало — строка в разбивку "не та дата", НЕ проваливается на следующее по приоритету правило (как и сегодня: раз правило её выбрало, именно его срок и применяется).
5. Группировка: если `force_tare_grouping` — объединить по контейнеру формата (`corrugated` для `general`, `tare_id` для `packaging`; `after_sale_movement` группировки не имеет, дедуп по `product`, как сегодня).
6. Хардкод-фоллбэк (`isMarketplaceStatus`/`isPresortStatus`/и т.д.) остаётся временной подстраховкой на переходный период — ровно тот же паттерн, что использовался весь текущий переход "от хардкода к админке".

**Важное изменение порядка:** сегодня фильтрация по дате (`offsetDays`) идёт ДО классификации; в новой схеме — ПОСЛЕ, потому что окно теперь принадлежит конкретному правилу, а не всему модулю. Это меняет порядок шагов во всех текущих build-функциях и требует полной регрессии на реальных данных перед переключением каждой кнопки (см. раздел 7).

### 4. Явные исключения — остаются специфичной логикой, не обобщаются

Проверено и сознательно НЕ тянем в движок, чтобы не сломать то, что généralize не ложится ровно:

- **Группировка ПМ по `transfer`, а не по таре/контейнеру.** ПМ группирует строки по номеру передачи (логистическая партия), это другое понятие, чем физическая тара/короб у остальных форматов. Чекбокс "группировать по таре" для ПМ не используется — группировка по `transfer` остаётся его собственной, захардкоженной логикой.
- **Порог суммы у ПМ — это сумма ПО ПЕРЕДАЧЕ (группе), не цена одной строки.** `price`-условие в Filter-правилах работает на уровне СТРОКИ (как у Упаковки: `price < 1000`). У ПМ порог 2000₽ — агрегат по уже сгруппированным строкам транзита, это принципиально другой уровень вычисления (после группировки, не до). Остаётся собственной проверкой ПМ, не выражается текущей схемой Filter-правил без отдельного "агрегатного" режима, который не обсуждался и не нужен больше нигде.
- **Разделение ПМ/Почта по одному и тому же правилу-совпадению** (`isMailRow`/`routeNumberFromMx`) — уже выражено zone-правилами (приоритет 17/18 в текущих данных), это уже отработавшая часть, просто получит новые поля (срок/т.д.) как любое другое zone-правило.

Уточнение к шагу 5 пайплайна: для строк, чья зона — ПМ или Почта, generic-группировка по контейнеру (шаг 5) не применяется вообще — вместо неё выполняется собственный, отдельный шаг сборки ПМ (группировка по `transfer`, порог по сумме передачи). Чекбокс "группировать по таре" на zone-правиле с целью ПМ/Почта просто игнорируется — это не конфликт, а явный приоритет PM-специфичной логики над generic-шагом.

## 5. Схлопывание кнопок

8 → 3 кнопки загрузки:

- **"Типовая выгрузка"** — `source_format = general` (ПМ-основной/Предсортировка/Маркетплейс+ПЦ/WMI/Без заказа).
- **"Упаковка / RWP"** — `source_format = packaging`.
- **"Движение после продажи"** — `source_format = after_sale_movement` (переводится на движок ради единообразия, хотя разделять сегодня не с кем — один rule с условиями "всё" на старте миграции).

ПМ теряет отдельную кнопку — его загрузка идёт через "Типовую выгрузку", второй файл (проверка отгрузки) становится отдельным действием (раздел 6).

## 6. "Проверить передачи на отгрузку" — новое отдельное действие

Не часть предпросмотра/сохранения загрузки. Отдельная кнопка в интерфейсе ПМ:

1. Оператор загружает тот же файл-отчёт отгрузки (ручная загрузка, без изменений формата) — **после** того как задачи ПМ/Почта уже созданы и сохранены (в отличие от сегодняшнего блокирующего шага перед сохранением).
2. Система берёт список АКТИВНЫХ задач с `task_type in ('Разбор ОПП // ПМ', 'Разбор ОПП // Почта')`, сопоставляет по номеру передачи (`source_tare_id`/`tare_id` = `transfer` из файла).
3. Найденные совпадения — `task_status` переводится в `'Завершено'`.
4. Старый `excludedTransfers`-фильтр (блокирующий сохранение) удаляется из загрузки ПМ целиком — этим занимается новое действие.

## 7. Порядок внедрения (чтобы не сломать прод)

1. **Схема** — миграция с новыми колонками `wms_routing_rules`, дефолты не меняют поведение существующих 18+ правил (`output_key` у всех остаётся `'zone'`, `source_format` проставляется вручную по текущему `target_task_type` для существующих правил, остальные новые поля — дефолтные/false/null = эквивалент сегодняшнего хардкода).
2. **Атрибут `price`** — добавить в build-time атрибуты, протестировать через Filter-правило на реальных ценах (begin/rollback), без активации в проде.
3. **Единая build-функция** — переводить по ОДНОМУ формату за раз, с полным regression-сравнением (старая функция vs новая на реальных активных строках) перед переключением кнопки на новую. Порядок: `packaging` (наименьший риск — уже доказанное совпадение Упаковка/RWP) → `general` (наибольший объём, 5 участков) → `after_sale_movement` (наименьшая ценность, но проще всего, раз нечего объединять).
4. **"Проверить передачи на отгрузку"** — отдельная задача, не блокирует остальное; можно делать параллельно с п.3.
5. **UI схлопывания кнопок** — только после того, как все 3 build-функции прошли на проде минимум один реальный цикл без хардкод-фоллбэка (т.е. движок правил реально решает 100% случаев, не хардкод).
6. Хардкод-функции (`isMarketplaceStatus` и т.д.) удаляются из кода только после подтверждённого нулевого использования фоллбэка в проде (см. `TEST_UPLOAD_DIAGNOSTIC_LABELS`/аналогичный мониторинг) — не раньше.

## Явно вне рамок

- Никакой автоматической/live-интеграции с отчётами WB — всё остаётся ручной XLSX-загрузкой.
- Агрегатные (по группе/транзиту) Filter-условия — не строятся, ПМ-порог остаётся хардкодом.
- `grouping_attribute`-механизм (уже мёртв, см. предыдущую сессию) — не восстанавливается.
