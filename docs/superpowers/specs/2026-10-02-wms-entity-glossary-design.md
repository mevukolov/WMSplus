# Словарь понятий WMS+ — единая модель сущностей

**Статус:** концептуальный словарь. Это не план миграций и не план рефакторинга
кода — фиксируем **общий язык понятий**, которым должна описываться вся система,
прежде чем унифицировать запросы и структуры данных на практике. Любые
технические изменения (новые таблицы, RPC, рефакторинг) — предмет отдельных
будущих задач, каждая со своей спекой/планом.

**Контекст:** система выросла из множества независимо написанных подсистем
(поиск, автосопоставление «Без ШК», разбор коробов, чистые списания, задачи,
Предсписок и т.д.), каждая из которых завела свою терминологию и свой способ
читать одни и те же по сути данные. Этот документ — попытка договориться, что
есть что, прежде чем стандартизировать доступ к данным.

## Центральная сущность: ШК

Всё остальное в системе крутится вокруг ШК — физической единицы товара со
своим штрихкодом. Сегодня ШК не существует как одна каноническая запись —
его состояние собирается по кускам из `shk_rep`, `wms_tasks.source_payload`,
`pure_losses_rep`, `2shk_rep` и `wms_task_nm_index`. Ниже — то, каким ШК должен
быть концептуально, независимо от того, как именно физически разложен сейчас.

**Атрибуты ШК:**

| Атрибут | Описание |
|---|---|
| НМ | ссылка на номенклатуру (см. ниже) |
| Статус движения | внешний трёхбуквенный код состояния (SGR/SMC/SAS/EPR и т.д.), приходит из внешней системы (WB), мы его не присваиваем, только считываем |
| Дата и время последнего движения | когда статус движения был обновлён в последний раз |
| Последний склад | `wh_id` — внешний идентификатор склада/ПВЗ, полученный из той же внешней системы |
| Списан | булево, **выводится**, а не хранится отдельным флагом: `true`, когда задача, держащая этот ШК, находится в зоне «Чистые списания» (`task_type`), см. ниже |
| tara_id | ссылка на тару, если ШК физически лежит в ней |
| mh_id | ссылка на МХ — либо прямое место (если ШК не в таре), либо то же место, где стоит текущая тара, скопированное на уровень ШК для удобства поиска «все ШК на этом МХ» без join через тару |
| Цена | |
| История обработки | список записей `{task_id, вердикт, сотрудник, время, комментарий}` — единственное место, где фиксируется результат нашей собственной работы с этим ШК. Первая запись может быть «рождение из БШК» (см. Предложение соответствия ниже) |

**Как ШК на самом деле становится «Списан» (реализовано 2026-10-05,
финальная версия после пересмотра первого захода от 2026-10-02):** не
отдельным булевым флагом и не авто-закрытием задачи системным вердиктом —
«Чистые списания» сделаны **ещё одной зоной разбора** внутри `wms_tasks`
(`task_type = 'Чистые списания'`, наравне с Предсортировкой/АВХ/Коробками на
входе), с собственным урезанным набором вердиктов (`ZONE_VERDICTS` в
`task-verdicts.js`) — в том числе новым «Отправлен на аннулирование»,
который схлопнул два прежних сценария «Отправлен на релиз» и «Аннулирование
после списания» в один, с автоматическим откладыванием на 2 дня.

Жизненный цикл остаётся прежним по смыслу — **выгрузка (задача) → может
повиснуть в предсписке → в какой-то момент всплывает в выгрузке чистых
списаний**, но переход теперь двусторонний и реализован как смена
`task_type`/`task_status`/`opp_verdict` **той же строки** `wms_tasks`, а не
созданием новой записи — поэтому вся история (`wms_task_history`,
`task_id`-based) переносится бесплатно, без копирования:

- **Вперёд** (`wms_pure_losses_absorb_shks`, запускается из обоих мест
  загрузки Excel-файла чистых списаний — `pure_losses.js` и открытия смены в
  `tasks.js`): если задача держала только этот ШК — она целиком
  перепрофилируется в зону на месте; если ШК был одним из нескольких в общей
  таре — он вынимается в отдельную новую строку (`split_from_task_id`),
  остальные товары тары не трогаются; если подходящей активной задачи не
  было вовсе (в т.ч. потому что задача уже была завершена раньше) — всё
  равно заводится/перепрофилируется запись в зоне, поиск кандидата намеренно
  не фильтрует по `task_status`.
- **Назад** (`save_wms_manual_upload`, срабатывает при ЛЮБОЙ обычной
  загрузке): если ШК, который сейчас числится в зоне «Чистые списания»,
  всплыл в какой-то другой выгрузке — задача переключается обратно в
  канонический `task_type` этой выгрузки тем же механизмом смены полей на
  месте.
- Разовый бэкофилл (2026-10-05) перенёс в зону пересечение с уже
  завершёнными на тот момент задачами: 3479 задач / 3902 уникальных ШК, по
  явному решению — все 6 вердиктов, не только «Нет на МХ/Не найден».
- В UI это не отдельная карточка-участок в «Предразборе», а отдельная
  вкладка «Чистые списания» верхнего уровня, группирующая задачи зоны по
  месяцу и числовому коду причины списания (`lr`) — так же, как раньше
  группировался сырой `pure_losses_rep`, только источник данных теперь
  `wms_tasks` и строки кликабельны (открывают обычную карточку задачи).
- Системный вердикт «Система - Автосписание» (первый, отменённый вариант
  реализации) полностью удалён — зона использует обычный, человеком
  выбираемый набор вердиктов, никакого auto-close нет.

**Важно:** статус движения (внешний) и вердикт (наш собственный, внутри Истории
обработки) — два разных понятия. Статус движения описывает, что происходит с
вещью по данным внешней системы; вердикт — что МЫ решили по итогам обработки
в конкретной задаче. Они обновляются независимо друг от друга.

**Проверено по факту (живая БД, 2026-10-02) — статус движения не льётся
непрерывно:**

- Обновление статуса движения происходит только через ручную загрузку
  оператором экспортного файла из внешнего BI-инструмента Superset
  (`handleActualizeSupersetFile` в `tasks.js`). Это нерегулярный,
  человеко-зависимый процесс, а не автоматический поток.
- Таблица `wms_superset_cache` уже сегодня дедуплицирована по `shk` и по
  форме почти точно совпадает с внешней половиной атрибутов ШК: `shk`, `nm`,
  `last_office` (= «последний склад»), `last_status` (= «статус движения»),
  `last_status_at`/`last_status_ts`. При реальном переходе на каноническую
  таблицу ШК бэкофилл этой части — не с нуля.
- Но на момент проверки этот кэш не обновлялся **3 недели** (последнее
  обновление 14 сентября, сегодня 2 октября) — это существующая проблема
  прод-системы, независимая от этой модели, но она означает, что «статус
  движения» у ШК физически не может быть свежее последнего ручного
  Superset-экспорта.
- `shk_rep` — изначально предполагался внешним фидом движений, но по факту
  это наш собственный узкий лог (5005 строк на 2026-10-02), содержащий
  только 3 типа операций: «Генерация ШК», «Генерация баркода», «Ожидает
  оприходования». Это готовая инфраструктура именно для «Стикер-события»
  (см. ниже) — просто раньше не было распознано как таковое.
- `nm_rep` по форме похож на `shk_rep`, но не обновлялся с 2026-06-03 —
  похоже на заброшенный/заменённый механизм, не стоит на него опираться.

## Номенклатура (НМ)

Справочник товаров. Один НМ может быть общим для нескольких ШК (разные
физические единицы одного и того же товара).

- `nm` (ключ)
- название
- бренд
- фото с карточки WB

## Задача

Задача — это **группировка ШК**, а не самостоятельный держатель состояния.
«Тарная» задача ничем принципиально не отличается от любой другой — это
просто задача, в которую попали ШК, последнее движение которых было
зафиксировано в одной таре.

- id
- тип / контекст создания
- список ШК, входящих в задачу прямо сейчас

**Задача не хранит свой вердикт, сотрудника или время обработки.** Всё это —
исключительно в Истории обработки конкретного ШК, с привязкой к `task_id`
этой задачи. Источник правды для статуса задачи (выполнена/в работе) —
всегда история её ШК.

Это уже проверенный принцип — именно так сейчас работает разбор коробов:
короб закрывается не потому, что у него появился «общий вердикт», а потому
что каждый ШК внутри получил свою запись в своей собственной истории.

**Чтение статуса остаётся быстрым:** вычислять статус задачи сканированием
истории всех её ШК при каждом чтении списка задач было бы медленно на
больших списках. Поэтому на задаче хранится денормализованная копия
статуса — но пишется она не отдельным шагом, а **в той же транзакции**, что
и запись в Историю обработки ШК. История остаётся единственным источником
правды (из неё денормализованную копию всегда можно пересобрать заново),
но повседневное чтение списка задач не требует join/сканирования.

## БШК (товар без ШК)

Фото/карточка товара, который ещё не идентифицирован как конкретный ШК. Не
является ШК сама по себе. Цель существования БШК — быть привязанной к
конкретному ШК (через присвоение стикера или через находку в задаче/списании)
и вернуться в обычный оборот.

- id
- наименование — присвоено оператором вручную при заполнении формы
- категория
- участок
- ответственный
- дата и время фиксации
- вероятная номенклатура — список кандидатов НМ от WB (`wb_nm_candidates`) +
  время последней проверки. Это именно *вероятные* названия/бренды, не
  факт — отсюда и работает автоподсказка при поиске совпадений
- присвоенный ШК — `null` по умолчанию; ссылка на ШК, с которым эта БШК была
  объединена

## Короб / Тара

Контейнер, хранящий внутри себя ШК. Входные коробки (на приёмке) и складские
тары (из задач) — одна и та же сущность по смыслу. ШК может свободно
извлекаться из тары и возвращаться обратно.

- id
- mh_id — где сейчас стоит этот короб/тара
- состав — не хранится отдельно, а выводится через `ШК.tara_id`

## МХ (место хранения)

Место, куда может быть положен и где может быть обработан ШК или целая тара
с ШК внутри.

- id
- источник — **наше** (управляется WMS+, например стеллажи зоны «Без ШК») или
  **внешнее** (складское место по данным WB)
- тип (полка/рэк/зона) и занятость — применимо только к «нашим» МХ; для
  внешних МХ мы не администрируем занятость и получаем всю информацию о
  нахождении там только из внешних источников

## Сотрудник

Оператор системы — человек, способный производить манипуляции с ШК или с
тарами, содержащими ШК.

- id, имя, роль

## Смена

Временной отрезок для разбивки статистики и логирования. Не несёт
самостоятельной бизнес-логики сверх роспуска сотрудников по датам.

- id, дата, склад, ростер (список назначенных сотрудников)

## Предложение соответствия

Кандидат на связь БШК ↔ ШК/Задача, сгенерированный автопоиском, **до**
подтверждения человеком. Отдельная сущность от Истории обработки — та
пишется только по факту подтверждённого действия, а Предложение соответствия
описывает ещё не принятое решение.

- id
- БШК, к которой относится предложение
- кандидат — ссылка на ШК (через задачу) или на запись списания
- оценка схожести (например по НМ/бренду/названию)
- статус: `pending` / `confirmed` / `rejected`

При подтверждении (`confirmed`) предложение превращается в запись в Истории
обработки соответствующего ШК и заполняет `БШК.присвоенный_шк`.

## Инциденты — три разных типа

Концептуально это не одна сущность, а три — форма данных у них разная:

- **Инцидент / Ошибка** — привязан к одному ШК: `{id, shk_id, описание, время}`
- **Два ШК** — привязан к ДВУМ ШК одновременно, у каждой стороны может быть
  своя привязка (фото-доказательство на сторону): `{id, shk_id_1, shk_id_2, время}`
- **Пустая упаковка** — привязан к одному ШК: `{id, shk_id, время}`

**Проверено по факту:** «Два ШК» и «Пустая упаковка» физически живут в ОДНОЙ
таблице (`2shk_rep`: `shk1`, `shk2`, `eventtype`, `media`, `media2`) — у
«Пустой упаковки» `shk2`/`media2` просто пустые. Решение: **не разводить
физически** — оставляем одну таблицу с дискриминатором `eventtype`, не
ломаем то, что уже работает. Разделение на два понятия остаётся только на
концептуальном уровне словаря. Также: сегодня нет отдельного текстового
«описания» на каждую сторону — есть только фото (`media`/`media2`), поэтому
атрибут «описание» из более ранней черновой версии убран как не
соответствующий реальным данным.

## Понятия, которые НЕ являются самостоятельными сущностями

Эти термины используются в обиходе, но растворяются в сущностях выше —
фиксируем явно, чтобы не плодить лишние таблицы/абстракции:

- **Списание** — не сущность, а состояние ШК (`Списан = true`, при этом
  «Статус движения» заморожен как статус на момент списания).
- **Стикер-событие** — не отдельная сущность, а первая запись в Истории
  обработки ШК (момент, когда Предложение соответствия для БШК подтверждено
  присвоением нового стикера, а не находкой в существующей задаче).
- **Предсписок** — не сущность, а альтернативный экран/вид для просмотра ШК
  и задач.
- **Предсписок-действие** — обычное действие с задачей в отдельном UI-контуре;
  попадает в ту же Историю обработки ШК, что и любое другое действие.
- **Внешние задачи WEEEK** — устаревший контур, исключён из модели как
  кандидат на последующий вывод из системы.

## Открытые вопросы (сознательно оставлены за скобками)

Эти моменты всплыли по ходу обсуждения — решили не включать в текущую модель,
подтверждено повторно при дотошном разборе рисков:

- «Клейм/Лок» задачи (`claimed_by`, `claimed_at`, `lock_until`) — временная
  блокировка задачи сотрудником, чтобы двое не работали над одной задачей
  одновременно. Реальный механизм в коде (`claimFlowTask`), но не включён в
  концептуальную модель как атрибут сущности.
- Приоритет, дедлайн и зона ответственности задачи (`priority_score`,
  `due_date`, `responsibility_zone`) — вычисляемые/операционные атрибуты
  задачи, оставлены вне текущей модели.
- Группировка дублирующихся инцидентов (`incident_group_id`, `grouping_key`,
  `grouping_confidence`) — не обсуждалась отдельно.

Если эти механизмы понадобятся для дальнейшей стандартизации запросов, их
стоит разобрать отдельным заходом, а не задним числом дописывать в этот
словарь.

## Риски перехода на эту модель

Зафиксировано при дотошном разборе 2026-10-02, до начала какой-либо
реализации.

**Что ломается, если менять всё сразу в проде:**

- Все существующие поисковые системы (6-7 штук, разобранные ранее) написаны
  под сегодняшние разрозненные таблицы — каждая требует переписывания.
- `opp_verdict`/`task_status` читаются напрямую в десятках мест (`tasks.js`,
  `search.js`, `opp_dashboard.js`, `opp_admin.js`, отчёты) — убрать эти
  колонки одним шагом значит одномоментно сломать мониторинг и дашборды, не
  обсуждавшиеся в рамках этого словаря.
- Разные потоки (quickNoShk, Предсписок-действие, Два ШК, разбор коробов)
  сегодня пишут историю в разной форме payload — унификация требует пройтись
  по каждому write-пути без пропусков, иначе часть истории тихо теряется.
- Нет изолированного стенда — прод используется живой сменой прямо сейчас.

**Первое решение по стратегии (принято, затем отменено 2026-10-02):**
собрать систему отдельно в новой схеме (`countour2`, не трогая прод),
подключить одним переключением, когда всё готово.

**Риски этой стратегии, из-за которых она отменена:**

- Пока отдельная система строится, прод живёт и меняется каждый день —
  новые ШК, задачи, инциденты появляются постоянно. Нужен реальный
  бэкофилл/сверка данных в момент подключения, а не просто переключение
  флага — иначе на старте новая система будет мгновенно устаревшей.
- Отдельная система с первого дня должна сама принимать те же источники,
  что и прод (ручная загрузка Superset-файлов, интейк БШК, записи
  инцидентов) — то есть повторно реализовать почти весь слой наполнения
  данными (`tasks.js`/`intake_search.js`) ещё раз, прежде чем новую систему
  вообще можно включить.
- Нужен явный момент «заморозки» или план дозаписи дельты при переключении.

**Финальное решение (2026-10-02): страглер-фиг вместо параллельной
системы.** Схема `countour2` создавалась (`202610020001`) и в тот же день
снесена (`202610020002`) как пустая, ничем не используемая — нулевая цена
отказа. Вместо неё — эволюционировать существующие таблицы `public.*` по
одному изолированному куску за раз, сохраняя старые интерфейсы рабочими,
пока не переведём всех потребителей. Ключевая находка, которая это
обосновывает: `wms_superset_cache` уже сегодня в проде почти полностью
совпадает по форме с внешней половиной атрибутов ШК (`shk`, `nm`,
`last_office`, `last_status`, `last_status_at`) — развивать её на месте
дешевле, чем копировать в пустую схему и строить питание данными с нуля.

**Пройденные изолированные шаги:**

1. Вынос `no_shk_matches` из JSON внутри `wms_tasks.source_payload` в
   отдельную таблицу `wms_match_suggestions` (2026-10-02) — это и есть
   «Предложение соответствия» из модели выше.
2. Перевод «Списан» с вычисляемого флага на полноценную зону разбора внутри
   `wms_tasks` (2026-10-05, см. «Как ШК на самом деле становится «Списан»»
   выше) — закрывает добрую часть описанного выше жизненного цикла ШК.
3. Сведение «статуса движения» и «последнего склада» на единый
   `wms_superset_cache` вместо копии-снэпшота в каждой отдельной задаче
   (2026-10-08). Write-путь уже существовал раньше, но был снесён вместе с
   мёртвым `quickNoShk` (dc65a11) как будто бы годный только для той
   фичи — восстановлен без привязки к ней. Читающие места (заголовок
   задачи, фильтр по статусу, карточки совпадений «Без ШК») теперь сначала
   смотрят в этот общий кэш и только потом откатываются на снэпшот.
   Расчётная/историческая логика (дата списания, записи истории) намеренно
   не тронута — там нужен снэпшот на момент времени, а не живое значение.
4. Зона/вердикт/статус переехали с группы (строка `wms_tasks`) на
   отдельный ШК (`wms_task_items`) — полная трёхфазная миграция
   (2026-10-09 — 2026-10-11, см.
   `docs/superpowers/specs/2026-10-08-wms-task-items-normalization-design.md`,
   `...-phase2-zone-design.md`, `...-phase3-residual-gaps-design.md`).
   Фаза 1 — таблица-зеркало `wms_task_items` + триггер + бэкофилл, без
   изменения поведения. Фаза 2 — зона на уровне ШК для «Чистые списания»
   целиком, включая общие тары: костыль `split_from_task_id` убран,
   вкладка «Чистые списания» и карточка/вердикт для разошедшегося ШК
   (составной id `"<task_id>::<shk>"`) переведены на `wms_task_items`.
   Фаза 3 — остаточные дыры после Фазы 2: хотфикс `auto_reopen_wms_tasks`
   (разошедшиеся отложенные ШК не возвращались в обработку — был активный
   баг в проде), `wms_search_tasks` учитывает состояние конкретного ШК,
   guard для «Отложить»/«Переоткрыть» на синтетической строке,
   вычисляемый агрегат `task_status` на родителе из детей. Сознательно
   вынесено за скобки: кластер ачивок/продуктивности
   (`buildStaffStats`/`eligibleTaskAchievements` и т.д.) считает работу по
   строке задачи, а не по ШК — отдельный продуктовый вопрос («что считать
   единицей работы»), не техническая миграция; не начато.
5. ШК получил постоянную идентичность, не зависящую от конкретной задачи
   (2026-10-12, см. `docs/superpowers/specs/2026-10-11-wms-shk-registry-design.md`).
   Новые таблицы `wms_shk` (идентичность + `current_task_id` как
   указатель-кэш «куда сейчас кликнуть», НЕ механизм защиты) и
   `wms_shk_history` (постоянный журнал, зеркалится ОДНИМ триггером на
   `wms_task_history` — ни один из существующих писателей истории не
   тронут). Реальная защита от двух активных задач на один ШК —
   частичный уникальный индекс на `wms_task_items(shk) where task_status
   <> 'Завершено'`, проверено на живых данных дважды, применилось без
   конфликтов. Бэкофилл: 110761 ШК, 286743 строки истории. Экран профиля
   ШК (UI) сознательно вне объёма — только данные, экран отдельным
   заходом позже.
6. Движок правил маршрутизации, Фаза 1 (2026-10-13, см.
   `docs/superpowers/specs/2026-10-12-wms-routing-rules-phase1-design.md`).
   Администратор настраивает правила (условие по статусу/таре,
   приоритет, целевая зона, группировка) через новую модалку в
   интерфейсе — осиротевшие ШК (без активной задачи) после актуализации
   Superset раскладываются по этим правилам автоматически, вместо
   хардкода под каждый тип выгрузки. `wms_pure_losses_absorb_shks` и
   `save_wms_manual_upload` не затронуты — работают как раньше,
   параллельно с новым движком. Фаза 2 (ретроактивная пересборка уже
   активных задач на любое изменение статуса + подключение обычной
   загрузки и всего «Предразбора» к этому же движку) — зафиксирована как
   следующий будущий заход, не начата.
